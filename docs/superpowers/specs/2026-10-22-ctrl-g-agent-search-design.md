# Ctrl+G: агентский поиск по всей истории

## Зачем

`Ctrl+G` сейчас переупорядочивает только видимый список: до 100 последних сессий или
группы текущего поиска (`src/ai.rs`, `spawn_ai_rank`). Переупорядочивание на практике не
используется. Нужно другое: описать сессию своими словами («где я обновлял котлин в инфре»)
и найти её во всей истории, даже если её нет на экране.

История большая: ~8 600 сессий Claude (15 ГБ) и ~1 250 сессий Codex (1,6 ГБ) на основной
машине. Точный ввод не работает, потому что формулировка запроса и текст сессии расходятся:
русский против английского, «котлин» против «Kotlin 2.4.20».

## Цели

- `Ctrl+G` → запрос на естественном языке → Enter → до 5 найденных сессий из всей истории,
  у каждой короткое «почему».
- Найденная сессия открывается по Enter так же, как из обычного списка; `→` открывает дерево.
- Ожидание — около 25–30 с, и оно не выглядит зависанием: видно, что агент сейчас ищет.
- Esc во время поиска останавливает агента.

## Не цели

- Переупорядочивание видимого списка — удаляется целиком.
- Свой индекс сессий, эмбеддинги, кэш описаний.
- Поиск без `claude` в PATH.

## Анти-цели

- Каждый поиск оставляет в истории свою сессию. Тогда следующий поиск находит её первой,
  потому что в ней процитирован запрос. Это уже случалось в kitty-agent-finder.
- Агент получает больше прав, чем чтение истории через `ccs search` / `ccs show`.
- Агент использует `ccs` другой версии, чем запущенный, и формат вывода не совпадает.

## Варианты

Рассматривали четыре способа, выбран четвёртый.

1. **OpenAI Decisions API, воронка в два прохода по локальному индексу.** Первый проход —
   заголовки всех ~9 800 сессий, по 250 вопросов `predicate` на запрос; второй — подробное
   описание лучших 250. Пробы: `choice` ограничен 255 вариантами; 256 вопросов `predicate`
   в одном запросе обрабатываются за ~0,9 с. Оценка: 2–4 с и ~$0,06 за поиск. Минусы:
   нужен индекс по 17 ГБ, при каждом поиске описания всей истории (включая рабочие
   сессии Avito) уходят новому поставщику, а модель видит только заголовки и первые реплики.
2. **ripgrep по словам запроса, затем Decisions API.** Дёшево, но «котлин» не находит
   «Kotlin». Для расширения запроса понадобилась бы вторая, текстовая модель.
3. **Decisions API по всему индексу за один проход.** ~2 млн токенов, ~$0,20 за поиск,
   те же вопросы с индексом и данными.
4. **Агент `claude -p` с `ccs search` / `ccs show` (выбран).** Сам переформулирует запрос,
   ищет на двух языках, читает найденное. Индекс не нужен, нового поставщика нет. Проба
   на двух запросах с известным ответом (haiku 5.5, облегчённый запуск): оба ответа на
   первом месте, 28–33 с, $0,004–0,005 за поиск, модель работает 8–9 с, остальное — поиски
   `ccs` (~2,7 с каждый по всей истории) и запуск `claude`.

Decisions API остаётся кандидатом только для быстрого переупорядочивания видимого списка,
а эту функцию удаляем.

## Как устроено

### Запуск агента

`claude` ищется через `which` (как сейчас). Аргументы:

```
claude -p "<запрос пользователя>"
  --model <model>                     # из файла конфигурации, по умолчанию claude-haiku-5-5
  [--effort <effort>]                 # из файла конфигурации, по умолчанию флаг не передаётся
  --system-prompt "<промпт ниже>"
  --tools Bash
  --allowedTools "Bash(<ccs> search:*)" "Bash(<ccs> show:*)"
  --strict-mcp-config --setting-sources "" --disable-slash-commands
  --no-session-persistence
  --output-format stream-json --verbose
stdin: /dev/null
```

- Рабочий каталог агента — `<temp_dir>/ccs-agent-search` (создаётся при запуске). Даже с
  `--no-session-persistence` `claude` сохраняет большие выводы инструментов в
  `~/.claude/projects/<cwd>/<id>/tool-results/*.txt`; отдельный каталог собирает этот мусор
  в одном месте, а `.txt` `ccs` не ищет. В промпте `--limit 10`, чтобы выводы были меньше.
- `<ccs>` — абсолютный путь `std::env::current_exe()`. Он же подставляется в системный промпт,
  чтобы агент вызывал тот же бинарь.
- `--bare` не используется: в этом режиме авторизация только через `ANTHROPIC_API_KEY`,
  а подписка не работает (проверено: «Not logged in»).
- stdin закрыт: без этого `claude -p` ждёт ввода 3 с.
- Окружение наследуется, так что `CCFS_SEARCH_PATH`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`
  действуют и на поиск агента.
- `--no-session-persistence` обязателен (см. анти-цели).

### Файл конфигурации

`$XDG_CONFIG_HOME/ccs/config.toml`, если переменная не задана — `~/.config/ccs/config.toml`
(и на macOS тоже). Первый файл настроек ccs; других настроек в нём пока нет.

```toml
[agent_search]
model = "claude-haiku-5-5"   # необязательно
effort = "medium"            # необязательно: low | medium | high | xhigh | max
```

- Файла нет — значения по умолчанию: `claude-haiku-5-5`, без `--effort`.
- Файл читается при каждом запуске поиска, поэтому правка действует без перезапуска ccs.
- Ошибка разбора (битый TOML, неизвестное значение `effort`) показывается в статус-баре
  вместо запуска агента: `config <path>: <ошибка>`. Неизвестные ключи — тоже ошибка
  (`deny_unknown_fields`), чтобы опечатка не терялась молча.
- Имя модели не проверяется: ошибку от `claude` показываем как есть.

Проба на одном запросе: `--effort low` — 50 с, `high` — 25 с, ответ одинаковый; поэтому
значение по умолчанию не задаём.

### Системный промпт

За основу — текст из пробы:

```
You find sessions in the user's Claude Code / Codex history. Tools: Bash, restricted to
`<ccs> search` and `<ccs> show`.
- `<ccs> search "<query>" --limit 10 [--regex]` prints JSONL matches (session_id, project,
  file_path, line_number, timestamp, content) and a summary line.
- `<ccs> show <file_path> --line N --context 3` prints the surrounding messages.
Work fast: in your FIRST turn issue 3-5 `<ccs> search` calls in parallel (Russian and English
phrasings, synonyms, product/tool names, a --regex alternation). Open a session with
`<ccs> show` only when snippets are ambiguous. Stop as soon as you are confident.
Final answer: ONLY a JSON array of up to 5 objects {"session_id": "...", "file_path": "...",
"why": "<10 words>"}, best match first, [] if nothing fits. No prose, no code fences.
```

### Поток и прогресс

Фоновый поток (как сейчас в `spawn_ai_rank`) запускает `claude` через `Command::spawn`,
читает stdout построчно (`stream-json`) и шлёт в канал события:

- `Progress(Vec<String>)` — запросы из `tool_use` с командой `<ccs> search "…"`: в статус-баре
  показывается `searching: "kotlin 2.4", "обновл.*котлин"…`;
- `Done(Result<Vec<AgentHit>, String>)` — из финального события `result`: JSON-массив
  разбирается тем же способом, что сейчас (`parse_ai_response` — первый `[` до парного `]`),
  только в `Vec<AgentHit { session_id, file_path, why }>`.

Отмена: общий `AtomicBool`, как у `SearchHandle` в `src/tui/state.rs`. Поток проверяет его на
каждой строке; при отмене `child.kill()` + `child.wait()`, ничего не шлёт. stderr сливается
отдельным потоком, чтобы не забился буфер, и попадает в текст ошибки.

Таймаут: 120 с, затем `kill` и ошибка `agent timed out`.

### Результат в интерфейсе

- Для каждого `AgentHit` строится `RecentSession` через `recent::extract_summary(path)`
  (заголовок, проект, дата, ветка). Делается в том же фоновом потоке, до отправки `Done`.
  Сессии, которых нет на диске, отбрасываются; если не осталось ни одной — сообщение
  «ничего не нашлось, уточни запрос».
- Результаты агента — отдельный вид (своё поле в `AiState`, своя ветка в рендере),
  под каждой строкой `↳ <why>`. Он показывается и поверх пустого запроса, и поверх
  текстового поиска; ни `recent.filtered`, ни `search.groups` не меняются, текстовый поиск
  может дорабатывать в фоне (снимок `original_*_order` и разделитель «ranked/unranked»
  больше не нужны). *Решение автора дизайна.*
- Состояния режима `Ctrl+G` (*решение автора дизайна*):
  - **ввод** (результатов нет): клавиши как сейчас — символы и `←`/`→` идут в поле запроса,
    Enter запускает поиск, Esc выходит из режима;
  - **поиск** (агент работает): Esc останавливает агента и возвращает в «ввод» с текстом
    запроса;
  - **результаты**: `↑`/`↓` — по списку, Enter — resume, `→` — дерево, ввод символа или
    Backspace — правка запроса и сброс результатов (возврат в «ввод»), Esc — выход из режима
    к исходному списку одним нажатием. Выход из дерева возвращает к результатам агента.
- Enter — resume выбранной сессии через существующий путь (`ResumeTarget`) на последней
  точке сессии (`uuid: None`, как из списка последних сессий), без форка. Поэтому номер
  строки или uuid сообщения агенту возвращать не нужно.
- Подсказки внизу: в «результатах» `[Enter] Resume  [→] Tree  [Esc] Back`; во время поиска —
  `[Esc] Cancel`.

### Что удаляется

`build_prompt`, `SessionContext`, `collect_session_context`, `SessionInfo`,
`ai_rank_candidates`, `rank_items`, `apply_ai_rank_to_*`, `original_recent_order`,
`original_groups_order`, `ranked_count` и разделитель в `render_search.rs`, вместе с их тестами.
Сброс AI-ранжирования при переключении `Ctrl+R` / `Ctrl+A` / `Ctrl+H`
(`invalidate_ai_rank` в начале этих обработчиков) больше не нужен: поиск агента не зависит
от фильтров.

## Проверка

- Юнит-тесты: разбор `stream-json` (прогресс из `tool_use`, финальный `result`, ответ с
  текстом вокруг массива, пустой массив, ошибка `is_error`), построение аргументов
  (`--no-session-persistence`, путь к `ccs`, разрешённые команды), отмена и таймаут против
  скрипта-заглушки вместо `claude`.
- Тесты состояния TUI: вход/выход из режима, Esc во время поиска останавливает поток,
  Enter после результата открывает сессию, Esc после результата возвращает исходный список.
- `cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test`.
- Вручную, на машине автора (это проверка разработки, не условие релиза): два запроса из
  пробы («ранжирование через модель решений от typesafe», «расширение raycast чтобы
  прыгать во вкладку kitty») находят `505ac6be` и `8d95fc28` первыми; после поиска в
  `~/.claude/projects` не появилось новых `.jsonl`.

## Остаётся на усмотрение исполнителя

- Точный текст системного промпта и лимит `--limit` в нём.
- Как именно отрисовать строку `↳ why` (цвет, усечение).
- Opencode: `file_path` вида `<db>#<session_id>` — `extract_summary` его не читает; строить
  `RecentSession` через `opencode_summary_to_recent` или отбрасывать такие результаты.
