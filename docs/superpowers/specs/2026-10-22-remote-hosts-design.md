# Поиск по сессиям на удалённых машинах

## Зачем

Сессии Claude, Codex и Opencode живут на нескольких машинах: на Маке и на Linux-машине
Z270XX. Сейчас `ccs` на Маке видит только локальные сессии. Чтобы найти разговор с Z270XX,
надо зайти туда по ssh и запустить `ccs` там, а для этого сначала вспомнить, на какой
машине он был.

Нужно: запускаешь `ccs` на Маке и в одной выдаче видишь сессии и с Мака, и с Z270XX.
У каждой строки видно, с какой она машины. Enter на удалённой сессии открывает её на той
машине, где она лежит.

## Цели

- Поиск и список недавних сессий по умолчанию охватывают все машины из конфига.
- Недоступная удалённая машина не замедляет выдачу: локальные результаты показываются
  так же быстро, как сейчас, удалённые добавляются, когда приходят.
- У каждого результата есть машина: в TUI это метка, в JSON поле `host`.
- Фильтр машин: все, только локальная, только удалённые, конкретная машина. В TUI это
  клавиша, в CLI флаг `--host`.
- Enter на удалённой сессии открывает `claude` / `codex` / `opencode` на той машине через
  `ssh -t`, в папке проекта, в текущем терминале. Resume с ветки дерева работает так же,
  как локально.
- Превью, дерево веток (Ctrl+B), подсчёт сообщений и Ctrl+A для удалённых сессий работают
  так же, как для локальных.
- CLI (`search`, `list`, `pick`, `show`) поддерживает машины тем же протоколом, что и TUI.

## Не цели

- Копировать или синхронизировать файлы сессий между машинами.
- Искать на удалённой машине, когда она недоступна (офлайн-кэш).
- Продолжать удалённую сессию на Маке.
- Открывать Claude Desktop-сессию с другой машины.
- Ставить или обновлять `ccs` на удалённой машине автоматически.
- Цепочки машин: удалённый `ccs` не ищет на своих удалённых машинах.
- Поиск в обратную сторону, с Z270XX по Маку. `hosts.json` живёт только на Маке и не
  синхронизируется на другие машины.

## Анти-цели

То, что будет провалом, даже если технически работает:

- Пока Z270XX недоступен, каждый новый запрос ждёт таймаут ssh.
- ssh спрашивает пароль или passphrase, его вывод попадает поверх TUI или TUI зависает
  на вводе.
- Поиск при наборе текста запускает на Z270XX `rg` на каждую букву, и старые запросы
  дорабатывают впустую.
- По сети гоняются полные тексты сообщений: для запроса «error» это 152 МБ.
- Курсор прыгает, когда приходят удалённые результаты.
- Агенты, которые вызывают `ccs search`, заметно замедлились без нужды (см. «Замер CLI»).
- Разные версии `ccs` на машинах тихо выдают неверные данные вместо понятной ошибки.

## Ограничения и замеры (2026-10-22)

| Что | Значение |
|---|---|
| Сессии на Маке | 15 ГБ Claude + 1,6 ГБ Codex |
| Сессии на Z270XX | 2,5 ГБ Claude + 0,7 ГБ Codex + `opencode.db` |
| Задержка Мак → Z270XX | ~105 мс (Tailscale direct, через WAN; Мак не в одной LAN) |
| `ssh Z270XX true` при открытом ControlMaster | 0,25 с |
| `ccs search ripgrep --limit 200` на Маке | 3,7 с |
| то же на Z270XX через ssh | 0,8 с (73 КБ вывода) |
| `ccs search error --full-content` на Z270XX | 1,5 с, 26 216 строк, 152 МБ |
| `ccs list --limit 100` на Z270XX | 5,5 с |

На Z270XX уже есть `ccs 0.16.0`, `rg`, `claude`, `codex`. `ccs` из `~/.cargo/bin` доступен
в неинтерактивном `ssh Z270XX '…'`. В `~/.ssh/config` для Z270XX включены
`ControlMaster auto` и `ControlPersist 1h`.

Выводы:

- Искать надо там, где лежат файлы. sshfs и `rg` по сети при 105 мс задержки неприемлемы.
- По сети ходят только сниппеты и метаданные. Полный текст сообщения подгружается
  по требованию.
- Список недавних сессий с удалённой машины догружается в фоне.

В коде `file_path` везде считается локальным путём. Превью, подсчёт сообщений
(`count_session_messages`), дерево (`SessionTree::from_file`), контекст для AI
(`collect_session_context`), форк и resume читают файл с диска. Ключи кэшей тоже
`file_path`: `latest_chains`, `automation_cache`, счётчики сообщений. Это основная
переделка: результат определяется парой «машина + путь».

Похожие инструменты: claude-devtools читает удалённые логи по SFTP; claude-hop
синхронизирует сессии через rsync и переписывает пути; в atuin есть фильтр
`filter_mode = host | global`, та же модель «эта машина или все». Встроенного поиска по
нескольким машинам в Claude Code нет (anthropics/claude-code#58039).

## Варианты

Рассмотрели пять, выбран A.

- **sshfs / `rg` по сети.** Каждое чтение файла идёт через WAN, поиск по 3 ГБ займёт
  минуты. Отброшен.
- **Синхронизация сессий на Мак** (rsync в фоне, поиск локальный). +3,2 ГБ на диске,
  данные отстают, локальный поиск становится медленнее. Единственный плюс — поиск при
  недоступной машине, он не нужен. Отброшен.
- **B. Отдельный ssh на каждый запрос** (`ssh Z270XX ccs search --wire …`,
  `ssh Z270XX ccs show …`). Почти нет нового кода. Но убитый ssh не останавливает удалённый
  `ccs`: без tty он не получает сигнал, и каждая набранная буква дорабатывает поиск на
  Z270XX до конца (на «error» это 1,5 с CPU). Каждое превью — новое подключение.
  Недоступность машины определяется заново на каждый запрос.
- **A. `ccs serve --stdio`: постоянный канал (выбран).** TUI держит одно ssh-соединение
  на машину. Запросы и ответы — JSON-строки с номером запроса. Есть отмена на удалённой
  стороне, превью и дерево по тому же каналу, состояние машины видно по состоянию
  соединения. CLI использует тот же протокол: открыл, один запрос, закрыл. Цена — больше
  кода: сервер с циклом запросов и клиент на каждую машину.

Выбран A: TUI ищет на каждую букву, и только A отменяет лишнюю работу на удалённой машине
и подгружает превью без новых подключений.

## Как устроено

### Машина как часть идентичности результата

Вводится тип машины: `Host::Local` или `Host::Remote(name)`, где `name` — алиас из конфига
(он же ssh-алиас). Все структуры, которые несут `file_path` сессии, получают `host`:
`RipgrepMatch` (или `SessionGroup`), `RecentSession`, `ResumeTarget`, `PickedSession`.
Все кэши и словари, ключом которых сейчас служит `file_path`, переходят на ключ
`(host, file_path)`. Дедупликация недавних сессий по `session_id` идёт внутри одной машины:
одна и та же сессия на двух машинах — две строки. Всё, что сейчас хранится по голому
`session_id` (`opened_sessions`, аргумент `return_from_resume`, множества `seen` при
дедупликации), переходит на ключ `(host, session_id)`.

Любая операция, которая читает файл сессии (превью, дерево, счётчик, контекст, resume),
для `Host::Remote` уходит в клиент машины, а не на диск. Это требование, а не пожелание:
вводится ключ `SessionRef { host, file_path }`. Он ключ всех кэшей, и его принимает каждая
функция, которая читает данные сессии. Новое место чтения файла без `SessionRef` не
написать, поэтому оно не обойдёт проверку машины.

Метаданные удалённой сессии, которые прислал сервер, локальное чтение диска никогда не
перезаписывает. Пример ошибки, которую это закрывает: фоновый `count_session_messages`
для пути, которого на Маке нет, вернул бы 0 поверх числа с сервера, и в строке было бы
«N/0». То же для `build_chain_from_tip` при раскрытии группы и для `get_full_content`.

### Конфиг машин

Изменено при реализации: машины перечисляются в `[[hosts]]` общего
`~/.config/ccs/config.toml` (`name`, необязательный `ccs_path`), который появился в `main`
вместе с Ctrl+G. Отдельного `hosts.json` нет. Остальное ниже (`CCS_HOSTS`, `CCS_SSH`,
`CCFS_SEARCH_PATH`) без изменений.

Моё решение: файл `$XDG_CONFIG_HOME/ccs/hosts.json` (по умолчанию `~/.config/ccs/hosts.json`;
на macOS тоже `~/.config`, не `~/Library`), формат JSON, потому что `serde_json` уже
в зависимостях:

```json
{
  "hosts": [
    { "name": "Z270XX" }
  ]
}
```

- `name` — ssh-алиас и метка в выдаче. Адрес, пользователь, ключ и ControlMaster берутся
  из `~/.ssh/config`.
- Необязательный `ccs_path` — путь к `ccs` на удалённой машине, по умолчанию `ccs`. Нужен,
  когда `ccs` не в PATH неинтерактивного ssh. Используется и в `serve`, и в `resume`.
- Переменная `CCS_HOSTS` переопределяет список: `CCS_HOSTS=Z270XX,other`,
  пустая строка — без удалённых машин. Нужна для тестов, агентов и быстрого отключения.
- Переменная `CCS_SSH` заменяет программу `ssh` (по умолчанию `ssh` из PATH). В тестах
  это скрипт, который отбрасывает опции ssh и имя машины и запускает остальное локально.
  Так одна и та же сборка команды проверяется и для `serve`, и для `resume -t`.
- Нет файла и нет переменной — удалённых машин нет, поведение как сейчас.
- Задан `CCFS_SEARCH_PATH` — удалённых машин нет, если `CCS_HOSTS` не задан явно.
  Существующие интеграционные тесты задают только `CCFS_SEARCH_PATH`. Без этого правила
  на Маке с настоящим `hosts.json` они ходили бы на Z270XX, и проверки вроде точного числа
  строк падали бы.
- `App::new` конфиг не читает. Список машин ему передаёт вызывающий (`main`). `App::new`
  вызывают около 158 unit- и snapshot-тестов, им конфиг машины разработчика не нужен.

Конфиг машин, клиент машины и сборка ssh-команды `ssh_command(host, mode)` живут в модуле
`src/remote/` вне TUI. Им пользуются TUI, CLI и resume, так что ssh-команда собирается
в одном месте. В `App` состояние машин — отдельная подструктура `HostsState`.

`ccs serve` конфиг машин не читает и ищет только по своим локальным путям, иначе машины,
которые указаны друг у друга, ходили бы по кругу.

### Транспорт

Команда по умолчанию:

```
ssh -o BatchMode=yes -o ConnectTimeout=3 -o ServerAliveInterval=5
    -o ServerAliveCountMax=2 -o Compression=yes <name> <ccs_path> serve --stdio
```

- `BatchMode=yes` — ssh никогда не спрашивает пароль или passphrase. Нет ключа — ошибка
  подключения, машина помечается недоступной, TUI не трогается.
- stdin и stdout ssh — трубы, stderr — отдельный поток, его последние строки идут
  в текст ошибки машины. На терминал TUI ssh ничего не пишет.
- `Compression=yes` — JSON-текст сжимается в несколько раз, при 105 мс задержки это важно.
- ControlMaster из `~/.ssh/config` переиспользуется автоматически.
- Если живой ControlMaster уже открыт, `ConnectTimeout`, `ServerAlive*` и `Compression`
  из командной строки не действуют: канал идёт через мастер с его настройками (проверено
  через `ssh -v`). Поэтому сжатие не гарантировано. Мастер, который протух после сна Мака,
  может висеть до ~45 с. Отсюда свой срок ccs на `hello` (см. «Клиент машины») вместо
  таймаутов ssh.
- ssh-процесс `serve` запускается в своей группе процессов (`process_group(0)`). Иначе
  Ctrl+C или Ctrl+\ в терминале во время resume дочерней сессии убили бы транспорты:
  `wait_child` заставляет игнорировать эти сигналы только сам ccs, а не его детей.

### Протокол `ccs serve --stdio`

NDJSON: одна JSON-строка — одно сообщение. Моё решение по форме:

- Первое сообщение сервера: `{"type":"hello","protocol":1,"ccs_version":"0.17.0"}`.
  Клиент сравнивает `protocol` со своим. Не совпало — машина в состоянии «несовместима»,
  в статусе `Z270XX: обнови ccs (<ccs_version из hello>)`, запросы не шлются. Старый `ccs`
  без `serve` завершится с ошибкой clap. Это тоже «несовместима», не «недоступна», но версию тогда
  показать нельзя: `hello` не пришёл, в статусе просто `Z270XX: обнови ccs`. Так будет
  с нынешним `0.16.0` на Z270XX, в нём нет `serve`. Разбор выхода до `hello` —
  в «Клиент машины».
- `protocol` совпал, а `ccs_version` отличается от локальной — машина работает, в статусе
  машины видна неблокирующая пометка о другой версии: правила вроде признаков
  автоматической сессии могут отличаться.
- Запрос: `{"id":7,"method":"search","params":{…}}`.
- Ответ: `{"id":7,"result":{…}}` или `{"id":7,"error":"…"}`.
- Отмена: `{"method":"cancel","params":{"id":7}}`. Сервер ставит флаг отмены
  у запроса 7 (тот же механизм `cancel: Arc<AtomicBool>`, что у локального поиска,
  с `child.kill()` для `rg`) и ответа на 7 не шлёт.
- Каждый запрос на сервере выполняется в своём потоке. Запись в stdout — под одним мьютексом,
  целыми строками.
- EOF на stdin — сервер отменяет всё и выходит.

Методы:

| Метод | Параметры | Ответ |
|---|---|---|
| `search` | `query`, `regex`, `project` (необязательно, см. Ctrl+A) | группы по сессиям: метаданные группы (с меткой `project`), `message_count`, сниппеты совпадений; признак `truncated` |
| `recent` | `limit`, `project` (необязательно) | список недавних сессий (поля `RecentSession` и метка `project`) |
| `show` | `file_path`, `line` или `uuid` | полный текст сообщения (`content`, `text_content`) |
| `tree` | `file_path` | готовое дерево (строки `SessionTree`) с превью узлов по 120 символов, как сейчас; `tip_uuid` и число веток |

Сниппеты в `search`: у каждого совпадения сервер присылает `text_content` и `content`,
обрезанные вокруг совпадения (как `extract_context` в CLI), с флагом
`content_truncated`. `message_count` сервер считает сам в том же запросе, чтобы клиент не
делал по запросу на каждую сессию. В метаданные группы входит всё, что TUI сейчас читает
из файла сессии: признак автоматической сессии (для Ctrl+H) и метка проекта `project`
(сейчас TUI считает её через `extract_project_from_path`, а тот читает файлы и базу Codex
и Opencode с локального диска). Для отметки форка у каждого совпадения есть флаг
`on_latest_chain: bool`, сервер считает его сам. Клиент по этим флагам заполняет
`latest_chains[(host, file_path)]`.

Параметр `full_content` (для CLI `--full-content`) отключает обрезку, но только для первых
`limit` совпадений после сортировки по времени на сервере. Так флаг работает для удалённых
машин так же, как локально, а объём ограничен тем `--limit`, который передал агент. Лимиты (символов на сниппет, совпадений на сессию,
сессий на ответ) выбирает исполнитель. Критерий: ответ на `search "error"` с Z270XX
укладывается примерно в 2 МБ до сжатия и приходит на Мак за 2–3 с на текущем канале.
Если на сессию отброшена часть совпадений, это видно в группе («показано 50 из 312»).

Сервер не вызывает никакие `std::process::exit` и не печатает в stdout ничего, кроме
протокола: существующие функции CLI, которые печатают или выходят, для `serve` надо
разделить на вычисление и вывод.

- `install_panic_hook` в `src/main.rs` сейчас ставится для всех подкоманд и пишет в stdout
  escape-последовательности терминала. Это сломало бы NDJSON. Для `serve` хук не ставится,
  либо хук ничего не пишет в stdout, когда stdout не терминал.
- Каждый обработчик запроса обёрнут в `catch_unwind`. Паника становится ответом
  `{"id":N,"error":"panic: …"}`, сервер продолжает работать.

Ответы сериализуются отдельными wire-структурами (модуль вроде `serve::wire` или
`remote::wire`). Они собираются из внутренних типов (`RecentSession`, `Message`, группы,
строки дерева) и поля `host` не содержат: машину знает клиент. Golden-JSON тест фиксирует
их форму. Любое изменение wire-структур поднимает `protocol`.

### Клиент машины

На каждую удалённую машину — объект клиента со своим потоком чтения и записи. TUI получает
ответы через mpsc, как сейчас получает результаты локального поиска.

Состояния машины: `Connecting`, `Ready`, `Down { since, reason }`, `Incompatible { version: Option<String> }`.

- Подключение начинается при старте TUI, параллельно с локальной загрузкой.
- `Down` ставится только в двух случаях: канал закрылся (EOF, ssh завершился) или `hello`
  не пришёл за N с после запуска ssh (свой срок ccs, около 3 с, моё решение; после него
  ccs убивает ssh-процесс и дожидается его). В `Down` запросы к машине не шлются,
  следующая попытка через 60 с (моё решение) или сразу, когда пользователь переключает
  фильтр машин (Ctrl+L).
- Выход ssh до `hello` разбирается по коду:
  - 255 — ошибка самого ssh, `Down`;
  - 127 или «command not found» в stderr — `Down` с текстом «ccs не найден»;
  - другой ненулевой код (например, clap «unrecognized subcommand», код 2) —
    `Incompatible { version: None }`, в статусе «обнови ccs»;
  - `hello` пришёл, но `protocol` другой — `Incompatible { version: Some(…) }`.
- Таймаут запроса — 10 с (моё решение). Он проваливает только этот запрос: ошибка видна
  в статусе машины, машина остаётся `Ready`, соединение не закрывается.
- `cancel` убирает id из множества ожидающих запросов клиента. Ответы на неизвестные id
  отбрасываются.
- При переходе в `Ready` (первое подключение и каждое переподключение) клиент сам шлёт
  `recent` и, если строка ввода не пуста и фильтр машин пропускает эту машину, `search`
  для текущего `search_seq`. Иначе запрос, набранный до подключения, `recent` при старте
  и `ccs pick "query"` с готовым запросом не дошли бы ни до одной машины: при старте все
  машины ещё `Connecting`.

### Поиск в TUI

`start_search` отправляет запрос локально (как сейчас) и в каждую `Ready`-машину,
которую пропускает фильтр машин. Номер `search_seq` общий. Предыдущий удалённый запрос
отменяется сообщением `cancel`.

Результаты хранятся по источникам: локальный и по одному на машину, все с текущим
`seq`. Каждый пришедший ответ с текущим `seq` пересобирает общий список групп: слияние,
сортировка по времени, фильтры (проект, автоматические сессии). Ответы со старым `seq`
отбрасываются. «Идёт поиск» в статусе означает, что не пришёл локальный ответ:
`is_searching()` по-прежнему смотрит только на локальный `search.current`. Ожидание
удалённых показывается отдельно, в статусе машин, и выдачу не блокирует.

`handle_search_result` сейчас на каждый результат сбрасывает `cursor`, `sub_cursor`
и раскрытые группы, чистит `latest_chains` и заново запускает поток подсчёта сообщений.
Теперь сброс только при начале нового `seq`. Следующий источник с тем же `seq` только
вливается и заново проходит фильтры, курсор привязан к группе. Локальный поток подсчёта
сообщений идёт только по группам `Host::Local`.

`reset_search_state` (Ctrl+C, стирание запроса до пустого) и `suspend_for_resume` сейчас
отменяют только локальный `search.current`. Теперь они ещё шлют `cancel` каждой машине,
у которой есть ожидающий запрос, и увеличивают `search_seq`. Иначе поздний удалённый ответ
с прежним `seq` заполнил бы группы, и при пустом вводе (в том числе после возврата из
resume) вместо списка недавних была бы старая выдача.

Курсор при пересборке остаётся на той же группе, ключ `(host, session_id)`. Если группы
больше нет, курсор встаёт на ближайшую по позиции.

### Недавние сессии

Пустой запрос: локальный список как сейчас. Параллельно `recent` в каждую машину.
Удалённый список приходит секунд через 5 и вливается в общий, отсортированный по времени
содержимого. Курсор привязан так же, как в поиске.

Удалённые строки лежат в отдельном буфере на каждую машину, не в `all` и не в `project`
у `RecentState`. Существующая фильтрация по проекту удалённые строки отбросила бы:
`apply_filter` берёт Claude-строки только из `project`, а Codex и Opencode из `all`,
и сверяет их с локальным `current_cwd`. Поэтому:

- `session_matches_project`, `group_matches_project`, `extract_project_from_path`
  и `detect_session_automation` применяются только к строкам и группам `Host::Local`;
- для удалённых строк ccs доверяет отбору по проекту на сервере и метке `project`,
  которую прислал сервер (и в TUI при отрисовке, и в `pick`);
- `total_count` = локальное объединение + сумма удалённых буферов;
- множество `seen` при дедупликации — по `(host, session_id)`.

### Отображение

- Удалённые строки получают короткую метку машины перед проектом, например `Z270XX`,
  отдельным цветом. Локальные строки без метки.
- Статус машин в строке состояния: `Z270XX: 37` (сколько пришло), `Z270XX: …` (ждём),
  `Z270XX: недоступен`, `Z270XX: обнови ccs`.
- Для машины в состоянии `Down` в TUI видна причина: строка подробностей с последними
  строками stderr или разбором кода выхода ssh.
- Превью удалённого совпадения со срезанным текстом показывает сниппет и подгружает полный
  текст через `show`, ответ кэшируется по `(host, file_path, uuid|line)`. Превью в дереве
  (сейчас `get_full_content` читает диск при отрисовке): `SessionTree` несёт `host`, для
  удалённой сессии `get_full_content` отвечает только из `content_cache` (как при
  предзаполнении у Opencode), а отрисовка без текста в кэше показывает `content_preview`.
  Диск при отрисовке не читается.
- Запросы `show` и для превью поиска, и для дерева шлются при движении курсора или
  в `tick()`, никогда из отрисовки. Множество ожидающих `show` с ключом
  `(host, file_path, uuid|line)` не даёт слать один и тот же запрос дважды.

### Фильтр машин (Ctrl+L)

Ctrl+L свободна. Она переключает по кругу: `Все → Локальные → Удалённые`. Если удалённых
машин больше одной, в круг добавляется каждая машина отдельно. Текущий режим виден
в строке состояния рядом с фильтром проекта. Без удалённых машин в конфиге Ctrl+L ничего
не делает, в подсказках её нет.

В режиме «Локальные» удалённые запросы не шлются. При переключении обратно на «Все»
текущий запрос отправляется на удалённые машины. Фильтр совмещается с Ctrl+A и Ctrl+H.
Если на момент переключения был AI-ранг, он сбрасывается через `invalidate_ai_rank()`,
как при других переключениях фильтров.

### Ctrl+A на удалённых машинах

Пути на Маке (`/Users/vkkovalev/projects/x`) и на Linux (`/home/materkey/projects/x`)
отличаются только домашней папкой (на обеих машинах разные имена пользователя). Поэтому
проект на удалённой машине сравнивается по пути относительно домашней папки своей машины:

- Клиент передаёт как `project` в `search` и `recent` текущую папку относительно своего
  `$HOME` (`projects/claude-code-fullsearch-rust`). Если текущая папка лежит вне `$HOME`,
  передаётся абсолютный путь.
- Сервер для каждой сессии берёт `cwd` из её записей, а не из закодированного имени
  каталога в `~/.claude/projects`: дефисы в имени проекта там неотличимы от разделителей
  пути. Берётся `cwd` первой записи, у которой он есть. Этот `cwd` сервер переводит в путь
  относительно своего `$HOME` (или оставляет абсолютным, если тот вне `$HOME`).
- Совпадение для Codex и Opencode — по тому же правилу, что локально у Codex
  (`path_is_within_project`): `cwd` сессии равен проекту или лежит внутри него.
  Сравниваются пути по компонентам, не строки по префиксу, иначе `projects/x` совпал бы
  с `projects/x-old`.
- Совпадение для Claude — только точное равенство `cwd` и проекта, по компонентам.
  Локально Ctrl+A для Claude совпадает только с папкой самого проекта (закодированный
  каталог), подпапки не попадают. Удалённо ведём себя так же.
- `path_is_within_project` (сейчас приватная функция в `src/tui/state.rs`) переезжает
  в общий модуль, которым пользуются и TUI, и `serve`. Копию не делаем.
- Проекты вне `$HOME` (например, `/Users/Shared/projects/avito-android`) совпадают только
  при одинаковом абсолютном пути, то есть с Linux-машиной обычно не совпадают. Это
  допустимо.

Локальная логика Ctrl+A не меняется. Но `toggle_project_filter` сейчас перезагружает
только локальный список. Теперь каждое переключение Ctrl+A ещё заново шлёт машинам
`recent` и, если ввод не пуст, `search` с новым `project` (или без него).

### Resume

Новая подкоманда `ccs resume --file <path> [--uuid <uuid>]` выполняет на своей машине то,
что сейчас делает `resume_inner`: находит папку проекта, при необходимости делает форк
JSONL и запускает агента. Источник (Claude / Codex / Opencode) определяется по пути, как
сейчас.

- На удалённой машине `ccs resume` работает в `ResumeMode::Exec` (Codex, как и сейчас,
  запускается дочерним процессом).
- При `Err` он выходит с ненулевым кодом, чтобы проверка `BOOTSTRAP_WINDOW` на Маке
  увидела неудачный запуск.
- Он никогда не спрашивает «Press Enter»: ждать ввода — дело ccs на Маке.
- С флагом `--host <name>` та же подкоманда на Маке сама делает ssh-переход: `ccs_path`,
  опции, экранирование, разбор кода 255. Команду собирает `ssh_command(host, mode)`
  из `src/remote/`, тот же, что у TUI.

Мак для удалённой сессии запускает `ssh -t <name> <ccs_path> resume --file … [--uuid …]`
(с опциями транспорта, кроме `BatchMode`). Удалённая сессия — терминальная
(`resume::runs_in_terminal`), поэтому `ssh` запускается дочерним процессом через тот же
путь, что сейчас `claude` / `codex` / `opencode` (`resume_child` и `wait_child`):

- игнор SIGINT/SIGQUIT в ccs, пока работает ребёнок, обработка Ctrl+Z, сброс ввода tty
  после выхода — как сейчас;
- overlay — после выхода всегда возврат в выбор сессии;
- обычный режим — возврат только после быстрого выхода (`QUICK_EXIT_WINDOW`), иначе ccs
  завершается;
- ошибка в окне `BOOTSTRAP_WINDOW` — неудачный resume, как сейчас; код выхода удалённого
  агента приходит через ssh. Ошибку самого ssh (255) показываем текстом «Z270XX: не удалось
  подключиться», а не как ошибку агента.

ssh склеивает аргументы в строку для удалённой оболочки, поэтому путь и uuid надо
экранировать для shell (в путях бывают пробелы, например `Application Support`).

Claude Desktop-сессия с удалённой машины не открывается: показываем ошибку в статусе,
как для других невозможных resume.

### CLI

- `search`, `list`, `pick` получают флаг `--host`, его можно повторять: `all` (по умолчанию),
  `local`, `remote`, имя машины.
- Строки JSON `search` и `list` получают поле `host`: `"local"` или имя машины.
- Итоговая запись `search` получает `hosts`: по каждой машине `name`, `status`
  (`ok` / `down` / `incompatible` / `timeout`), `shown`, `error`. Так агент видит, что
  Z270XX не ответил.
- CLI ждёт удалённые машины параллельно с локальным поиском, потом выводит то, что есть.
  Предел ожидания (моё решение): 5 с для `search`, 10 с для `list`. Мерили `ccs list`
  на Z270XX: 5,5 с ещё без сети, так что с пределом 5 с он почти всегда кончался бы
  `timeout`. `list` входит в замер «до и после».
- `--limit` применяется к слитой выдаче, отсортированной по времени.
- `show` получает `--host`. По умолчанию `local`, чтобы старые вызовы не изменились.
- `pick` выводит строку `host: <name>` (для локальной `host: local`).
- `.claude/skills/ccs/SKILL.md` и `.agents/skills/ccs/SKILL.md` обновляются: поле `host`,
  `ccs show --host <host>`, флаг `--host local` для быстрого поиска.
- Сценарии skill после `ccs pick` для удалённой сессии (моё решение, в согласии с выбранным
  resume): «Read here» читает через `ccs show --host`, а не через Read по `file_path`.
  «Enter session (overlay)» запускает `ccs resume --host <host> --file … [--uuid …]`
  вместо локального `launch-resume.sh`, а не собирает `ssh -t` в shell. ssh-команду
  строит сам ccs. `launch-resume.sh` вызывает только SKILL.md в `.claude/skills/ccs`,
  поэтому сценарий меняется только там.

### Замер CLI до и после

Пользователь просил замерить время ответа CLI до и после, чтобы решить, оставлять ли
удалённые машины в CLI по умолчанию.

Замер: `hyperfine` (или 10 повторов вручную) на Маке, 3 запроса — редкое слово,
частое слово (`error`), regex. Сравнить:

1. текущий релиз (`ccs` без изменений);
2. новый `ccs` с `--host local`;
3. новый `ccs` по умолчанию (Z270XX доступен);
4. новый `ccs` по умолчанию, Z270XX недоступен (например, `CCS_HOSTS` с несуществующим
   алиасом).

То же для `ccs list`.

Результат — таблица в описании PR или в разборе к нему. Умолчание для CLI меняет
пользователь по этим цифрам; переключить его должно быть изменением одной константы.

### Связь с Ctrl+G

В `docs/superpowers/specs/2026-10-22-ctrl-g-agent-search-design.md` (параллельная работа)
Ctrl+G становится агентом, который вызывает `ccs search` / `ccs show`, а AI-ранжирование
видимого списка удаляется.

- Агент получает удалённые результаты через обычный `ccs search` и должен передавать
  `host` в `ccs show --host`. Его промпт и разбор ответа учитывают поле `host`.
- Метода для контекста AI-ранжирования в протоколе нет: ранжирование удаляется планом
  Ctrl+G. Пока оно не удалено, удалённые сессии ранжируются без первых реплик (только по
  проекту и заголовку).

## Тесты

- Протокол и сервер — интеграционный тест: `ccs serve --stdio` с `CCFS_SEARCH_PATH`
  на фикстуры, запросы `hello`, `search`, `cancel`, `show`, `tree`, EOF.
- Клиент — `CCS_SSH` на фейковый ssh, который запускает `ccs serve --stdio` локально:
  слияние результатов, отбрасывание старого `seq`, курсор на месте после прихода удалённых.
- Недоступная машина — `CCS_SSH` на программу, которая сразу падает, и на программу,
  которая молчит: машина уходит в `Down`, локальные результаты не задерживаются.
- Медленное подключение — фейковый ssh задерживает `hello`: после `Ready` клиент сам
  шлёт `recent` и `search` для текущего `search_seq`, запрос, набранный до подключения,
  доходит до машины.
- Несовместимая версия — фейковый ssh печатает `hello` с другим `protocol`.
- Старый `ccs` без `serve` — фейковый ssh печатает ошибку clap и выходит с кодом 2:
  машина `Incompatible { version: None }`.
- Wire-структуры — golden-JSON тест на форму ответов `search`, `recent`, `show`, `tree`.
- Существующие тесты — с `CCFS_SEARCH_PATH` и без `CCS_HOSTS` удалённых машин нет,
  даже если на машине есть `hosts.json`.
- CLI — `--host`, поле `host`, `hosts` в итоговой записи, таймаут.
- Resume — экранирование пути с пробелами в команде ssh; удалённая сессия → child;
  ssh 255 → ошибка подключения. Unit-тесты на разбор кода 255 и на выбор пути для
  удалённого resume. В CI стоит CRAP-проверка: новые непокрытые функции с CRAP > 15 валят
  сборку.
- Ручная проверка на реальном Z270XX: поиск, превью, дерево, resume Claude и Codex,
  overlay, отключённый Tailscale. Ctrl+C во время resume через `ssh -t` в overlay:
  машины остаются `Ready`.

## Что оставлено исполнителю

- Точные лимиты сниппетов и числа совпадений в ответе `search` (по критерию 2 МБ / 2–3 с).
- Как именно разделить существующие функции CLI на вычисление и вывод.
- Формат сериализации дерева.
- Цвет и точное место метки машины в строке, текст статуса.
- Порядок коммитов. Разумный порядок: вынос общих помощников (`path_is_within_project`)
  → тип `Host`, `SessionRef` и ключи кэшей без поведения → `src/remote/` (конфиг машин,
  `ssh_command`) → `serve` → клиент и TUI → resume → CLI → документация и skill.
